# HappyHouse

Property consultancy & property management platform for HappyHouse (Thane, Maharashtra).

This is the initial scaffold: database schema, a working FastAPI backend, and a working
Next.js frontend covering the full core loop — **admin logs in → adds a property → it
appears on the public site automatically → a visitor enquires → the admin sees it.**
That loop (spec §45, the project's acceptance test) is functional end-to-end in this
scaffold. Polish items are listed under "What's next" below.

## Architecture

```
happyhouse/
├── docker-compose.yml   # One-command local hosting (see below)
├── .env.example         # Docker Compose secrets template
├── database/
│   ├── schema.sql      # DDL — run this first
│   └── seed.sql         # Clearly-labeled demo data (remove before production)
├── backend/              # FastAPI + SQLAlchemy + MySQL
│   ├── Dockerfile
│   ├── app/
│   │   ├── main.py       # App entrypoint
│   │   ├── models.py     # SQLAlchemy models (mirrors schema.sql)
│   │   ├── schemas.py    # Pydantic request/response contracts
│   │   ├── auth.py       # Password hashing + JWT session cookie + CSRF verification
│   │   ├── limiter.py    # Shared rate-limiter instance
│   │   ├── config.py     # Env-driven settings
│   │   └── routers/      # auth, properties (public), admin_properties, enquiries, settings, uploads
│   ├── scripts/
│   │   ├── create_admin.py    # Interactive CLI to create the first owner account
│   │   └── reset_password.py  # Interactive CLI to reset a forgotten password
│   └── tests/             # pytest suite (in-memory SQLite, no MySQL needed to run)
└── frontend/              # Next.js 14 (App Router) + TypeScript + Tailwind
    ├── app/                # Pages: /, /properties, /properties/[slug], /services,
    │                       # /about, /contact, /admin/*
    ├── components/         # PropertyCard, HeroSearch, EnquiryForm, admin components
    └── lib/                # Typed API client + shared types
```

## Local setup

### Option A — Docker Compose (one command)

Requires [Docker Desktop](https://www.docker.com/products/docker-desktop/) running.

```bash
cp .env.example .env
```

Edit `.env`: set `MYSQL_ROOT_PASSWORD` to whatever you want (this is a fresh,
separate MySQL instance inside Docker — it won't touch your existing local
MySQL install), and generate a real `JWT_SECRET_KEY`:
```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Then:
```bash
docker compose up --build
```

This starts MySQL (seeded automatically from `database/schema.sql` and
`database/seed.sql` on first boot), the FastAPI backend on `:8000`, and the
Next.js frontend on `:3000`. First run takes a few minutes; subsequent
`docker compose up` runs are fast.

Create your admin login (in a second terminal, once containers are up):
```bash
docker compose exec backend python -m scripts.create_admin
```

Visit `http://localhost:3000` (public site) and `http://localhost:3000/admin/login` (admin).

**Notes:**
- The Dockerized MySQL runs on host port `3307` (not the default `3306`), so it
  won't conflict with the MySQL you already have installed locally. The backend
  connects to it internally via Docker's network (`mysql:3306`), so this only
  matters if you want to connect a GUI tool (DBeaver, MySQL Workbench) from your
  host machine — point it at `localhost:3307`.
- `docker compose down` stops everything but keeps your data (in a named
  volume). `docker compose down -v` also wipes the database — use that if you
  want a clean slate.
- To rebuild after changing dependencies (`requirements.txt`/`package.json`):
  `docker compose up --build`.
- Logs: `docker compose logs -f backend` (or `frontend`, `mysql`).

### Option B — run natively (no Docker)

You already have MySQL installed locally, so this works too:

#### 1. Database

```bash
mysql -u root -p < database/schema.sql
mysql -u root -p < database/seed.sql   # optional — demo data for development
```

#### 2. Backend

```bash
cd backend
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

Edit `.env`:
- Set `DB_PASSWORD` to your local MySQL root password (leave blank if none).
- Generate a real secret: `python -c "import secrets; print(secrets.token_hex(32))"` → paste into `JWT_SECRET_KEY`.
- Leave `CLOUDINARY_*` blank if you don't have an account yet — the admin property
  form will show a clear setup message rather than failing silently when you try
  to upload an image; everything else works without it.

Create your admin login:
```bash
python -m scripts.create_admin
```

Run the API:
```bash
uvicorn app.main:app --reload --port 8000
```
Visit `http://localhost:8000/docs` for interactive API docs (auto-generated by FastAPI).

#### 3. Frontend

```bash
cd frontend
npm install
cp .env.example .env.local   # NEXT_PUBLIC_API_URL=http://localhost:8000
npm run dev
```
Visit `http://localhost:3000` for the public site, `http://localhost:3000/admin/login` for admin.

## Running tests

```bash
cd backend
pip install -r requirements-dev.txt
pytest tests/ -v
```

30 tests covering auth (login, rate limiting, CSRF enforcement, password change), property CRUD (creation, slug collisions, publish/delete, location-privacy coordinate handling), and enquiries (submission, rate limiting, admin status workflow). Runs against an in-memory SQLite database — no MySQL connection needed to run the suite.

## What's next

Real remaining gaps — see `docs/TECHNICAL_REPORT.md` §25–26 for the full, honest list:

1. **Admin password reset via email** — there's now a self-service "change password" (when logged in) and a CLI recovery script (`scripts/reset_password.py`) for a fully-forgotten password, but no email-based reset flow (would require SMTP infrastructure this project doesn't set up).
2. **Multi-language support** — Marathi/Hindi toggle for the public site, given the actual Thane audience.
3. **Email notifications** — new enquiries currently surface via the dashboard only, not email.
4. **Wider test coverage** — the current 30 tests cover the highest-risk paths (auth, CSRF, core property/enquiry flows); areas, settings, image upload, and CSV import/export don't have dedicated tests yet.

Everything else — image upload, admin CRUD for properties/areas/settings, CSV import/export, Docker Compose hosting, SEO (sitemap/robots/structured data/Open Graph previews), light/dark mode, header/footer/filters/lightbox/similar-properties/favorites/comparison, rate limiting, CSRF protection, and a real embedded map (OpenStreetMap, no API key) — is implemented. See `docs/ADMIN_GUIDE.md` for how to use it and `docs/TECHNICAL_REPORT.md` for the full technical picture.

## Connecting with 99acres / MagicBricks / Housing.com

None of these portals offer a public API for pushing or pulling listings — the
only "integrations" available are paid scraping services (against their terms)
or a paid broker/business account with each portal's own proprietary bulk-upload
tool. Given that, here's what's actually built:

- **Outbound compare links** on every property page — site-scoped search links to
  each portal for the same locality/property type (`components/property/ComparePortalLinks.tsx`).
- **schema.org structured data** (JSON-LD) on every property page — the real,
  standardized way listing aggregators and search engines discover and parse
  property data.
- **`sitemap.xml` / `robots.txt`** — generated dynamically from published
  properties, so crawlers (including those portals', if they choose to index you)
  can find every listing.
- **CSV export** (`GET /api/admin/properties/export.csv`, button in the admin
  properties table) — download all your listings in a generic CSV shape to
  manually feed into whatever bulk-upload format your 99acres/MagicBricks/Housing.com
  broker account provides. You'll need to map columns to their specific template —
  we can't know that format without a business relationship with each portal.
- **CSV import** (`POST /api/admin/properties/import.csv`, button in the same
  table) — bulk-add properties you already have data for (e.g. from your own
  existing listings elsewhere, typed up yourself) without re-entering each one by
  hand. Imported rows land as unpublished drafts for review before going live.
  This is not a scraper — it only accepts data you supply.

## Do-not-do reminders carried from the spec

No fake testimonials, statistics, or reviews are anywhere in this codebase. All
business-identity fields (`site_settings`) are empty until you fill them in via
`/admin/settings`. Demo properties in `seed.sql` are prefixed `[DEMO]` and must be
deleted before going live.
